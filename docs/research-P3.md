## 1. 研究背景与目标

### 1.1 项目现状（v0.2.0 已交付）

SmartNoteGen 已完整落地 **P0 + P1 + P2**，形成「程序化 MIDI 生成 → 渲染 WAV → Suno 合规导出 → 可选 AI 扩编曲」的完整本地创作闭环。

**当前能力全景：**

| 层 | 能力 | 命令 |
|---|---|---|
| 生成 | 程序化多轨 MIDI（和弦/旋律/贝斯/鼓）、music21 乐理旋律 + 变奏 | `generate midi` / `generate melody` |
| 批量 | 四维度随机化（和弦/节奏/风格/旋律）、seed 可复现、失败隔离 | `batch` |
| 风格 | 4 基线预设（pop/rock/electronic/classical）+ 自定义注册 | `--style` |
| 乐理 | 平行五度/八度检测、对位、转位、节奏型库 | `--voice-leading` 等 |
| DSP | 归一化 -1dBFS、淡入淡出、可选 EQ/压缩 | `pipeline` |
| 渲染 | FluidSynth 真实渲染、双音色库、路径分级探测 | `render` |
| 导出 | Suno 合规（10-30s 纯器乐、无混响）、WAV/MP3 | `export suno` |
| AI | MusicGen 扩编曲（chroma 0.706）、DiffRhythm 歌曲草稿 | `ai musicgen` / `ai diffrhythm` |
| 工程 | 输出管理（project-date/命名/元数据）、错误码 0-9、日志分级、覆盖率 91% | — |

**技术基线：** Python 3.12 · 源码 6018 行 · 21 测试文件 3268 行 · 241 用例全绿 · 覆盖率 91% · module/ 8GB（含 AI 权重）。

## 2. 用户画像与工作流分析

### 2.1 核心用户：独立创作者

- **目标**：用 AI + 本地工具快速生成歌曲旋律与器乐素材，上传 Suno Pro 做最终风格化与合成。
- **痛点（从 P0-P2 需求与 Open Questions 归纳）**：
  1. 产出物是**文件**，需要**手动**拿到 Suno 上传——缺自动化衔接
  2. 生成后**无法本地试听/预览**（无波形、无频谱、无播放）
  3. 批量生成后**挑选困难**（一堆文件，看不出哪个好）
  4. 参数**心智负担重**（和弦/BPM/调式/小节数……新手难上手）
  5. 无**版本管理**（迭代创作时难以对比不同版本）
  6. 无**灵感/动机库**（好的动机无法沉淀复用）

### 2.2 工作流缺口分析（当前→期望）

```
当前：
  生成 → 渲染 → 导出 → 【手动拷贝到 Suno】→ 手动试听挑选

期望：
  生成 → 渲染 → 导出 → 【自动/半自动上传 Suno】→ 本地试听预览 → 挑选 → 迭代
              ↑___________ 缺口 1：预览/试听 ___________↑
              ↑________________ 缺口 2：Suno 衔接 ________________↑
              ↑______________ 缺口 3：挑选/版本管理 ______________↑
```

## 3. P3 候选方向研究（5 大方向）

### 方向 A：本地预览与试听体验（最高频痛点）

**问题**：当前 CLI 只产出文件，用户无法在本地"听效果"。

| 子项 | 内容 | 复杂度 |
|---|---|---|
| A1 | **HTML 波形/频谱预览页**：生成后自动产出 `preview.html`，内嵌音频 `<audio>` + 波形图（waveform） | 低 |
| A2 | **本地播放**：`play` 子命令调系统播放器（Windows `start` / `os.startfile`）试听 WAV | 低 |
| A3 | **音频特征摘要**：RMS/峰值/频谱分布/时长，导出到 metadata，辅助挑选 | 低 |
| A4 | **MIDI 可视化**：钢琴卷帘图（piano roll）渲染为 SVG/PNG | 中 |

**价值**：直接解决"生成后无法快速判断好坏"的核心痛点，提升创作效率。
**技术**：waveform 用 numpy 降采样 → 内嵌 base64；无需新依赖（纯 stdlib + 已有 numpy/soundfile）。
**风险**：低。

### 方向 B：Suno 自动化衔接

**问题**：产出物需手动上传 Suno，打断创作流。

| 子项 | 内容 | 复杂度 |
|---|---|---|
| B1 | **Suno 官方 API 集成**：需确认 Suno 是否开放官方 API（当前主要靠网页/第三方） | 中-高 |
| B2 | **导出包一键打包**：把 10-30s 片段 + 元数据打包成可直接上传的 zip/目录 | 低 |
| B3 | **上传清单生成**：`export suno --batch` 批量导出后生成上传清单（CSV/JSON），指引用户在 Suno 逐个上传 | 低 |

**价值**：若 Suno 开放 API，自动化上传是"杀手级"能力；否则退化为"打包 + 清单"辅助。
**风险**：Suno API 可用性不确定（需调研）；第三方接口有封号/不稳定风险。
**技术**：B2/B3 低复杂度；B1 依赖外部调研。

### 方向 C：创作辅助与灵感管理

**问题**：缺乏动机沉淀、参数引导、版本对比。

| 子项 | 内容 | 复杂度 |
|---|---|---|
| C1 | **动机/灵感库**：把好的生成结果（MIDI + WAV + 参数）存入可检索库，支持按风格/和弦/seed 检索 | 中 |
| C2 | **参数引导**：交互式 wizard（`init` / `new`）引导用户一步步输入，降低新手门槛 | 中 |
| C3 | **版本对比**：同一 seed 不同参数迭代时，自动对比版本差异（参数 diff + 音频特征 diff） | 中 |
| C4 | **AI 风格建议**：基于 DiffRhythm 的 prompt 生成，或风格推荐的规则引擎 | 中-高 |

**价值**：让工具从"单次生成器"升级为"创作工作台"，沉淀用户资产。
**技术**：C1 基于现有 metadata.json + SQLite/JSON 索引；C3 基于 metadata 对比。
**风险**：中（范围易蔓延）。

### 方向 D：生成质量与多样性增强

**问题**：当前生成器相对程序化，音乐性/多样性有上限。

| 子项 | 内容 | 复杂度 |
|---|---|---|
| D1 | **更多 AI 模型接入**：MusicGen stereo / 更高质量模型 / 新开源模型（如 Stable Audio、udio 类） | 中-高 |
| D2 | **AI 旋律生成**：用 LLM/模型直接生成旋律动机（替代纯程序化），与 MusicGen 扩编曲衔接 | 中 |
| D3 | **风格库扩展**：国风/爵士/环境/放克等更多基线 + 节奏型库扩充 | 低-中 |
| D4 | **对位/和声增强**：四声部和声、更复杂对位规则 | 中 |
| D5 | **人声/歌词**：DiffRhythm 歌词建议、押韵检查 | 中 |

**价值**：提升产出上限，但边际收益递减、成本较高。
**技术**：D3 低复杂度；D1/D2 依赖模型选型与显存。
**风险**：中-高（AI 模型迭代快、权重下载大）。

### 方向 E：工程化与分发（P2-3 深化）

**问题**：打包/分发/配置体验尚未完全打磨。

| 子项 | 内容 | 复杂度 |
|---|---|---|
| E1 | **打包验证**：build_package.ps1 在干净环境产出可执行 CLI，含 module/ 资源相对性说明 | 低 |
| E2 | **配置向导**：`config init` 升级为交互式向导（检测 SoundFont/fluidsynth/espeak，引导配置） | 低-中 |
| E3 | **卸载/健康检查**：`doctor` 子命令一键检测环境（fluidsynth/SF2/AI/显存/依赖），输出诊断报告 | 低 |
| E4 | **CI/CD**：GitHub Actions 跑 lint + 测试 + 覆盖率门禁 | 低-中 |

**价值**：让项目更易分发、更易排障，是"可发布"的基础。
**技术**：低复杂度，纯工程增量。
**风险**：低。

按 **价值（V）× 成本（C）× 风险（R）** 综合评分，V 高、C/R 低者优先。

| 方向 | 价值 | 成本 | 风险 | 综合优先级 | 理由 |

| **A 预览/试听** | 高 | 低 | 低 | ★★★★★ | 直击最高频痛点，纯增量，无新依赖 |

## 5. 推荐 P3 路线（建议）

### 5.1 建议冲刺划分

**P3 一期：创作体验闭环（方向 A + E）—— 价值高、成本低、风险低**

```
P3-A1  HTML 预览页（波形+频谱+播放）
P3-A2  play 子命令（本地试听）
P3-A3  音频特征摘要（写入 metadata）
P3-E3  doctor 子命令（环境健康检查）
P3-E2  config init 交互式向导
```
- 退出标准：`generate/render/pipeline` 后自动产出预览页；`play` 可播放；`doctor` 输出诊断；全量 241 测试保持全绿 + 新增用例。

**P3 二期：创作工作台（方向 C）—— 价值高、范围需控制**

```
P3-C1  灵感库（SQLite + 检索）
P3-C3  版本对比
P3-C2  参数引导 wizard（可选）
```
- 退出标准：灵感库可存取检索；版本对比可输出 diff；wizard 可引导生成。

**P3 三期：Suno 衔接（方向 B）—— 依赖外部调研结论**

```
P3-B2  导出包一键打包（低复杂度，先行）
P3-B1  Suno 官方 API 集成（需调研 API 可用性后决定）
P3-B3  批量上传清单
```
- 退出标准：打包 + 清单可用；API 集成仅在确认官方开放后实施。

### 5.2 不建议优先投入

- **方向 D（生成质量）**：AI 模型迭代快、权重下载大、显存受限（8GB），边际收益不如体验优化。可作为 P3 后续探索，不做 P3 主线。

## 6. 技术可行性验证（P3 一期 spike 建议）

| spike | 目的 | 验证项 |
|---|---|---|
| **S-A1** | HTML 预览页可行性 | 用 numpy 降采样波形 + base64 内嵌，单文件 HTML 无外部依赖，浏览器可直接打开 |

**结论**：P3 一期技术风险极低，无新重型依赖，可立即启动。

## 7. 风险与开放项

| 风险 | 等级 | 缓解 |
|---|---|---|
| Suno API 可用性不确定 | 高（仅影响方向 B） | P3 一期不含 B1；先做 B2/B3 低风险项 |
| P3 范围蔓延（C 灵感库） | 中 | 每项独立验收、增量交付；C 作为独立冲刺 |
| module/ 体积 8GB 分发 | 中 | 打包时说明权重不入库、按需下载 |
| 新增 UI 化倾向 | 中 | 保持 CLI 心智模型，预览页为"产物"而非交互 UI |

---

## 8. 结论

**P3 主线建议：方向 A（预览/试听）+ 方向 E（工程化/doctor）作为一期，方向 C（创作工作台）作为二期，方向 B（Suno 衔接）视 API 调研而定。**

这份研究聚焦"把生成能力变成可用的创作体验"，在保持 CLI 心智模型、不引入重型依赖、不破坏既有 241 测试的前提下，最大化用户价值。
